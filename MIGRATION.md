# Replit → GitHub / Vercel migration checklist

**Preparation only.** The existing Replit deployment, its database, storage, secrets, and scheduled jobs must remain connected and unchanged until a separately tested destination is ready. Pushing source to GitHub does not migrate production data or make this API Vercel-compatible.

## Safe order of operations

1. **Review the export:** check Git's staged file list and commit history for secrets, personal data, database dumps and generated artifacts before pushing. Include source (`artifacts`, `lib`, `scripts`, schema, lockfile, app assets, API specification/generated clients) but not runtime credentials or production data. Large documents, films, and media remain in company Google Drive and are not copied to this repository. The ignored `attached_assets` folder is not included. The demo seed is included unchanged at the user's direction; review its contact names and email addresses before redistributing or reusing those sample records.
2. **Keep Replit running.** Do not delete `.replit`, disconnect its storage/database, change DNS, or run seed/cleanup against live data. Check whether Replit production already contains the newest nullable isolation columns; development schema state alone is not proof.
3. **Provision destination infrastructure:** production-like isolated Postgres; long-lived API host or tested serverless conversion; storage provider; verified Resend sender; optional identity provider; Google Sheet/Apps Script integration. Configure secrets separately for preview and production, and restrict preview DB/storage.
4. **Back up and rehearse:** take a point-in-time, encrypted production DB backup and object inventory/backup; validate restoration into a **separate** staging environment. Compare table counts, project links, media objects and permissions. Rehearse additive schema changes and report any legacy rows/constraints that require remediation—never overwrite live production with development records.
5. **Deploy staging:** route the Vercel static frontend and API under one HTTPS origin, then test login/invites/reset, project isolation, saves, uploads/downloads, exports, Google Sheets, scheduled jobs and PDF builds. Ensure only one scheduler runs. Test both authorized and cross-project-denied requests.
6. **Plan cutover and rollback:** schedule a short change freeze or incremental replication, capture a final backup and object delta, migrate without truncation, reconcile records/files, and switch DNS/rewrite traffic only after acceptance. Keep Replit available and its backups intact for rollback; document how to switch traffic back and stop the **new** schedulers to avoid double sends. Monitor errors and data drift before retiring any service.

## Important limitations

- No live database contents, uploaded files, Replit secrets, or production migration history are embedded in Git. The example seed at `scripts/src/seed.ts` is **not** a production backup and should never be run on an existing customer database.
- The source contains Replit-specific config and runtime integration code. The repository is exportable but is **not yet a verified one-click Vercel deployment**. A separate runtime adaptation and staged migration are required.
- Never claim the GitHub branch is pushed until its remote branch has been verified; Git export and Vercel cutover are separate approvals.
